# Certificate Pin Rotation — Android

Owner of record: whoever is on release duty.
Source of truth: `native-app/plugins/withNetworkSecurityConfig.js`.
Enforced by: `native-app/plugins/__tests__/networkSecurityConfig.test.ts` (CI job `mobile`).

## Why this document exists

Certificate pinning is the only control in the mobile app that fails **silently
in the safe direction**, which makes it the one most likely to be quietly dead.

- An **expired** `<pin-set>` is *ignored* by Android. The app keeps working; it
  simply validates against the system trust store like any unpinned app. There
  is no crash, no log, no user-visible symptom. Pinning is just gone.
- A **wrong** pin fails in the opposite direction, and does so totally: every
  TLS connection to `furlpay.com` fails, on every installed copy of the app, and
  the only fix is a store release. There is no server-side rollback.

Those two failure modes are why rotation is a written procedure rather than a
one-line edit, and why the expiry date is checked at build time.

## What is pinned, and why roots

`furlpay.com` is served by Vercel behind Let's Encrypt. Vercel rotates the leaf
certificate roughly every 90 days and Let's Encrypt rotates intermediates on its
own schedule, so pinning either would brick the app on a rotation nobody
controls. The pins are therefore the **SPKI SHA-256 of the trust anchors**:

| Pin | Role |
| --- | --- |
| ISRG Root YR | the anchor `furlpay.com` currently chains to |
| ISRG Root X1 | cross-signer — continuity for classic LE chains |
| ISRG Root X2 | LE's EC root — backup if issuance moves |

Three anchors, not one. A single pin means one CA rotation bricks every
installed app; the test asserts at least two.

## Build variants

| Source set | Config | Cleartext |
| --- | --- | --- |
| `app/src/main/res/xml/` | pinned | **denied everywhere** |
| `app/src/debug/res/xml/` | pinned (same anchors) | permitted for `localhost`, `10.0.2.2`, `127.0.0.1` only |

Both files are generated by the config plugin at `expo prebuild` time —
`native-app/android/` is gitignored and regenerated, so the checked-in plugin is
the only place a change can be made durably.

The dev-host exception used to ship in the **release** config, justified in a
code comment as "harmless in release: these hosts only exist on a developer
machine". That reasoning does not survive contact with a phone: on-device,
`localhost` and `127.0.0.1` are *the device*, and a malicious co-resident app
can bind a port there. Exploiting it still required influencing the base URL,
which is compiled in — so this was hardening rather than a live path — but it is
now simply absent from release builds (FURL-007).

Debug builds keep pinning for `furlpay.com`. The relaxation is scoped to the dev
hosts, not to production, so a debug build pointed at the real API is still
pinned.

## Build-time expiry guard (FURL-006)

`assertPinsNotNearExpiry()` runs inside the plugin's `withDangerousMod`, i.e. on
every `expo prebuild`, and therefore on every EAS build and every CI run of the
`mobile` job.

- expiry in the past → **throws**, the build fails
- expiry within `PIN_EXPIRY_WARN_DAYS` (180) → `console.warn`, build succeeds

The window warns rather than throws deliberately: a hard failure inside the
rotation window would block an incident hotfix over pins that are still valid.
The hard failure is reserved for pins that have actually lapsed.

## Rotation procedure

Start this **at the first warning**, not at expiry. A rotation needs a store
release, and store review is not on your schedule.

1. **Re-verify the live chain.**

   ```sh
   openssl s_client -connect furlpay.com:443 -servername furlpay.com -showcerts </dev/null
   ```

2. **Compute the SPKI SHA-256 for each anchor** you intend to pin. For each
   certificate in the chain (and for each published root you are adding):

   ```sh
   openssl x509 -in root.pem -pubkey -noout \
     | openssl pkey -pubin -outform der \
     | openssl dgst -sha256 -binary \
     | openssl enc -base64
   ```

   Compare the result against the published root fingerprints on
   <https://letsencrypt.org/certificates/>. Do **not** copy a pin from a blog
   post, an old commit, or a model's memory — a wrong pin bricks every install.

3. **Add the new pin alongside the old ones.** Never replace in the same
   release. There must be an overlap window in which both the outgoing and
   incoming anchors are pinned, or users on the old build lose connectivity the
   moment issuance moves.

4. **Bump `expiration`** in both `NETWORK_SECURITY_CONFIG` and
   `NETWORK_SECURITY_CONFIG_DEBUG`. Keep them identical — the test asserts the
   two configs pin the same anchors, because divergent sets are how a bad pin
   reaches production unnoticed.

5. **Run the tests.**

   ```sh
   cd native-app && npx jest plugins/__tests__/networkSecurityConfig.test.ts
   ```

6. **Verify on a device before release.** Install the release build and confirm
   real traffic to `furlpay.com` succeeds. A pin error surfaces as a generic
   network failure, so an untested pin looks exactly like an outage.

7. **Ship, then wait.** Only remove a retired pin once the release carrying the
   new one has meaningful adoption. Removing early strands everyone who has not
   updated.

## What not to do

- Do not remove pinning to fix a connection problem. Diagnose the chain first;
  an unpinned release cannot be un-shipped.
- Do not pin a leaf or an intermediate. Vercel and Let's Encrypt both rotate
  those without notice.
- Do not add a cleartext exception to the release config. If a build needs to
  reach a plaintext host, that belongs in the `debug` source set.
- Do not extend the expiry date without re-verifying the pins. The date is a
  dead man's switch, and moving it without checking defeats its purpose.
